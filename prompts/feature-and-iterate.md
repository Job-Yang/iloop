# 做需求 · 小迭代 · 重构（按需加载）

> 何时读：命中 `core.feature`（新需求）、`core.small_iter`（小迭代/文案样式）、`core.refactor`（重构回归）这几类"动手改代码"的 flow 时。这三类的共性是 L2：最小改动 + 编译 + 按目标验证、每步可回滚、范围限在已对齐任务内。

## 通用骨架（三类都适用）
1. **先理解现状，别急着写**：读相关代码、入口、状态、数据流，搞清"改这里会牵动什么"。缺 PRD/接口/设计稿先按澄清 gate 问，不带歧义开干。
2. **定最小验收**：动手前一句话说清"怎么算完成"（可验证硬指标），收口逐条核对。
3. **最小改动**：只改达成目标必需的代码，不顺手重构无关部分、不加投机抽象。跟随既有风格。
4. **编译**：走 `python3 -m cli invoke build`，看 success markers（BUILD SUCCEEDED + 产物存在），不只看 exit code。
5. **按目标取证**：逻辑/数据类看关键日志（`invoke logs`），界面类才截图（`invoke screenshot`），不默认三件套全跑。
6. **整体复核后收口**：执行 `global-review prepare` 看完整 diff、共享定义、删除逻辑和调用方；逐项绑定验证证据后才允许 `wrapup`。牵连主链路或需要真机能力时升级。

## feature：新需求开发
- 先把**需求边界**和**涉及的入口/状态/数据流**理清。缺 PRD 或接口定义就先问，不猜着做。
- 实现走最小改动；编译通过后启动验证，按需求性质选证据：逻辑/数据看日志，界面看截图。
- 验收对照需求目标逐条核。
- 升级时机：PRD/接口缺失、依赖未就绪、需要后端联调。

## small_iter：小需求迭代（文案/样式/微调）
- 改动小就别上重流程。最小改动 + 编译，有可见改动时模拟器快速看一眼即可。
- 不牵连主链路、不涉及硬件/权限就**不切真机**。
- 升级时机：改动牵连主链路或需要真机能力。

## refactor：重构回归影响面
- 不按“最后改了哪个文件”判断影响。先让 `global-review prepare` 读取从基线到当前的完整 diff，识别改动定义、仓内调用方、共享边界与删除行为，再挑受影响主链路逐个运行态回归。
- 每个影响项必须通过 `global-review record target=... evidence=...` 绑定证据；删逻辑时说明原服务对象和替代路径。未完成时 `wrapup` 代码级拒绝。
- 范围不确定、跨模块影响不清时，**先给影响面分析再升级**，不要盲目大改。
- 行为基线优先：重构不改外部行为，回归要证明关键入口行为不变（编译/测试 + 主链路验证）。
- 升级时机：跨模块影响不确定、或涉及不可控第三方组件。
- 影响面/崩溃归因等更细的工具链见 `triage-impact.md`。

## 编码风格
- 跟随既有代码风格（命名、注释密度、惯用法），不顺手重构无关代码、不加投机抽象。
- 构建/运行/取证的具体操作（模拟器 vs 真机、证据策略）见 `build-and-run.md`。
