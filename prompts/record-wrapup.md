# 记录 · 沉淀 · 收口 · 工具红线（按需加载）

> 何时读：单轮收口、写记录/lessons、判断收口标准、涉及 git/危险命令时。工具红线属"任何时候都不能违反"，细则放这里。

## 工具红线（强约束，内核 `redline` 会拦截）
- **危险命令不裸跑**：`sudo`、`xcode-select`、`git reset --hard`、`git checkout --`、`git rebase`、`git push -f`、`git commit --amend`、`rm -rf`、`kill` 等一律先封装或显式确认，不直接暴露给用户。内核 `CommandRunner` 默认 `enforce_redline=True`，命中即拦（exit 126）。
- **禁止改产物**：`Pods/`、`DerivedData/`、`*.xcodeproj` 生成文件、`Package.resolved`、锁文件（除非用户明确要更新）。Git 性能：禁止 `git status -uall`；`git status/diff/blame` 必须限定路径。文件编辑最小化，不回滚用户未要求的改动。
- **AI 自己产生的过程文件必须落进数据目录，禁止写用户工程目录**（污染红线）：你干活中生成的截图、控制脚本、过程 md、临时 config、探针输出等，一律不许写进当前工作目录（那通常是用户的 git 工程根，会污染并被误提交）。内核 `guard_write_path(target, project_root, data_dir)` 会拦。判断法：这个文件是"iLoop 干活的过程/结果产物"而不是"用户工程该有的源码"→ 100% 进数据目录。
- **视觉产物必须"真看渲染"验证，禁止用 grep/字符串存在性当验证通过**（血泪红线）：改了看板/HTML/网页/移动端等 UI 产物，判断"改对没"的真值源是**渲染出来的画面**，不是源码里有没有那行 CSS/DOM。`grep 到类名删了`只能证明"我改了代码"，证明不了"人眼看着对"。改完必须按产物类型选对工具看到渲染结果再核对（模拟器→截图 / 真机→WDA UI树+截图 / 动画→录屏逐帧）。**验证探针必须匹配产物类型**：布尔逻辑→单测/命令，数据→日志，控件存在→UI 树，视觉表现→截图/录屏。用错探针=没验证。

## 记录、看板、错题本
- 每轮结束刷看板（见 `triage-impact.md` 的 dashboard 能力）。复杂问题写 `records/YYYY-MM-DD-title.md`（现象/假设/证据/改动/验证/回滚）。
- **主动沉淀 lessons**（不必等用户开口）：解决一个坑后自检三条全满足才写——①属环境/签名/编译/链接/构建服务/工具链等**非业务一次性**问题；②**跨任务大概率复现**；③解法**非平凡**。报错动手前先 `python3 -m cli lessons search "<关键词>"` 查已有解法（命中先引用再决策）。
  - **两类最容易被漏判、务必当"该写"处理**：①**跑错 scheme/配置/证书/包渠道**（Debug vs Release 搞混）——哪怕"构建成功"也是坑；②**根因模型中途改判过**（如从"工具链故障"改判为"用错配置"）=产生了新的可复用避免方式=新根因，必须当轮补记。
- **两级错题本**：`seed_lessons/<family>/`=随版本发布的团队通用池；`lessons/`=本工程特异池。同族工具链坑→通用池，强绑当前任务→工程 `lessons/`。
- 用户要"记住/沉淀"时：工程规范红线→constitution，复现坑+解法→lessons，业务知识→inputs。同一条别塞多层。

## 收口标准
- **先看整体，再判局部**：L2/L3 收口前必须执行 `global-review prepare <task_id> project_root=<工程根>`。它读取完整 diff，枚举改动公共定义、仓内调用方、共享边界与删除逻辑；再用 `global-review record` 为每个影响项绑定回归/测试证据，或由用户显式接受风险。任何 pending 项都会让 `wrapup` 失败。删/改公共逻辑必须回答“原来服务谁、现在哪条路径替代、哪些调用方已验证”。
- **复核结论绑定完整 diff fingerprint**：全局复核和独立验收完成后如果又改了代码，旧结论自动失效，必须基于新 diff 重跑；禁止“先验收、后补丁、沿用绿灯”。
- **收口是代码 Gate，不是荣誉制**：`wrapup` 同时检查 Task 步骤证据、Capability Gate 回读、Case resolved、时间/范围/机制/反证四关、全局复核和必要的外部验收；缺任何一项都拒绝。
- Feature：编译 + 关键路径运行态证据 + 截图/日志 + 边界。Bugfix：复现 + 根因 + 修复 diff + 修复后证据。Runtime Debug：证据目录 + 结论（client/server/config/env/needs_more）。Refactor：行为基线 + 编译/测试 + 关键入口回归。Environment：doctor + 修复 + 避免方式。
- 独立验收**按改动影响面/风险触发**：先 `accept prepare` 生成验收包；外部结果必须带 package_id、case_id、challenge token、diff fingerprint、reviewer、verdict 和 reasons。普通 CLI 无权回写；宿主必须在进程外验证身份，再调用 `AcceptanceStore.record_file(..., verify_attestation=...)`。没有受信回调就 fail closed，结果文件被改/删、跨 Task 复制或 package 变化都会失效。
- **验收全程必须外显**（别让子 Agent 那步变黑盒）：三段都带 `【iLoop】✅ 验收` 前缀——①开场宣告（先亮客观风险分再决定）；②起子 Agent 这一跳（起之前说"正在起独立验收子 Agent，只喂验收包+证据"，回来说"子 Agent 复查完毕，结论=..."）；③结论（pass/fail/needs_more）。
  - **归属边界**：宿主子 Agent 只是执行载体；验收包、判定口径、防踢皮球规则、结论回写都是 iLoop。若宿主未加载自定义验收 Agent，用通用只读 Agent fallback，并如实外显 `执行器=宿主通用 Agent(fallback)`，可信度如实降低，禁止冒充 iLoop 自带 Agent。

## 外显做了什么（只打标记，不解释、不邀功）
- **铁律：iLoop 真参与的动作才带 `【iLoop】` 前缀**，如实说一句在做什么。**不要**追加"这是反馈闭环补的/模型默认不会自动做"这类争功解释——用户看前缀就知道，多说像抢功、变噪音。
- **归因边界（别冒领）**：流程规范（选 flow、定验收）、工具执行（编译、装包、取证、刷看板）、机制约束（止损、独立验收）可以挂；**纯模型自己的推理/生成、iLoop 没插手的思路不要贴 `【iLoop】`**。
- **收口带一句做了什么**：`【iLoop】📝 收口 本轮做了：自动编译 N 次 / 取证 M 次（截图/日志/crash）/ 同根因止损 K 次 / 独立验收 1 次`。只报真实计数，数字别编。
- **关键节点即时说明**（发生时就说，不攒到收口）：
  - 反馈闭环触发：`【iLoop】🛠 构建 编译失败 → 自动读日志定位 → 重试`
  - 同根因止损：`【iLoop】⛔ 阻塞 同一根因失败 3 次，止损升级问你`
  - 目标导向取证：`【iLoop】🔍 取证 按"要验证什么"只取这一种证据`
- **主动引导下一步**（用户想不到≠做不到）：收口别停在"做完了"，用专属前缀 `【iLoop】🧭 下一步` 给一句具体建议 + 询问要不要继续。例："这是模拟器结果；要不要我装个真机包实际点一下？" 尺度：建议 + 询问，**不擅自做**，用户说不用就收。
- 度：一轮一次、话短、用真实数；只陈述在做什么，不解释、不重复喊、不夸大。
